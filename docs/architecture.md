# den architecture (milestones 1 and 2)

How den's modules fit, which seams tests go through, and where each upcoming
ticket plugs in. Terms are CONTEXT.md's; the binding decisions are in
`docs/specs/0001-den-milestone-1.md` and, for Linear Workflows and Landing
Groups, `docs/specs/0002-den-milestone-2.md`.

## Data flow

```

                           │
  keys, ticks, finished ──►│ App::handle(Event) ─► (ViewModel, Vec<Effect>)
  operations (Events)      │                          │            │

                                                                      Owners with a Linear Workflow)
App, on Started:         Effect::LoadCache (before Effect::Survey) ─► Event::CacheLoaded ─►
                         CachedObservation::restricted_to_linear (each Owner's Linear Workflow, workspace
                         and the Linear sources it reads) ─► cache::merge_linear(App.unshown_linear) if
                         Linear answered first ─► missing Linear sources not yet fetched ─► shown with its age
App, on Started / `r`:   Effect::SurveyLinear (only when the config has Linear Workflows) and
                         Effect::Survey; the worker runs them concurrently, so either may answer first.
                         Refused (queue full): every Linear source failed for that survey

                         LinearReads), per Linear source; nothing shown: App.unshown_linear, merged into

                         Viewers::of(Observation), App.policies, upstreams, now) ─► ordering::order ─► view

                         ctx.policy(owner).review / held_repos; a member that would Merge "lands with")

                         Landing Group and the members' own Decisions: Land, Mark for release; then
                         .start) ─► the other kinds
App, once both surveys of a round answered (#37): cache::settle_member_states (drop states of PRs no

                         ─► Effect::StoreCache
App, on `u` (sidebar, fork row): UpstreamTargets toggled ─► decide again ─► Effect::StoreUpstreams ─► Event::UpstreamsStored
App, on `c` (launch):    handoff::inspect_request ─► Effect::InspectLaunch ─► handoff::inspect (Workspace,
```

Milestone 2 (#31) widened the shapes without changing behaviour: the
Observation carries a Linear part (empty), coverage reserves Linear source
kinds (none recorded), `decide` takes `Viewers` (the GitHub viewer) and
`Policies` (each Owner's Linear Workflow policy: empty for every Owner, and
the empty policy changes nothing), and a Job record's subject is a
`JobSubject` (a GitHub Work Item). The milestone-2 table below says where each
later ticket fills them in.

#32 (the Linear tracer) fills in the first of them: a Linear Workflow block
per Owner in the config, the read-only `LinearSource` port and its HTTPS
adapter, the Linear viewer and assigned Linear Issues in the Linear part,
`Viewers.linear`, `WorkItemId::LinearIssue` (workspace + permanent ID, under
its Owner), Implement for an assigned Linear Issue, and the Linear glyph and
workflow markers. The policy is still empty for every Owner.

The milestone-2 wave #33–#36, merged together (integration branch
`integrate/m2-wave3`), fills in the rest of the reading side:

- **Start (#33):** the team-states and start-team-issues Linear sources, the
  config's team and state names checked against Linear, Start for an offered
  unassigned Linear Issue, and Start ordering.
- **Linear data in the cache (#34):** Linear data merged per Linear source
  with its own age, dropped when the Linear viewer changes.
- **Landing Groups (#35):** attachments, the pure correlation step, members
  and hints, and the Repo Scope of a Linear Issue.
- **Workflow review rules (#36):** exact-head approval, awaiting re-review,
  Request review, Held Repos and suggested reviewers.

`LinearWorkflowPolicy` now carries `start`, `review`, `held_repos`, (#37)
`release_state`, (#40) `landing_order` and (#74) `parked_states`, each mapped
from the config by `LinearWorkflow::policy`; the empty policy offers no Start,
has no review rules, holds nothing, names no release state and parks nothing.

#37 adds the decisions on top: a member that would Merge "lands with" its
Linear Issue, the Linear Issue offers **Land** or names its blocking members,
and **Mark for release** rests on members read merged by number after the
survey (`Observation.member_states`).

`main` only wires: XDG paths, log, config, ports, and the terminal loop. The
loop checks for a termination signal (SIGTERM, SIGHUP, SIGINT, SIGQUIT) before
every input wait, so the terminal is always restored, and hands Effects to a background `runtime::Worker` so the UI stays
responsive while `gh` runs. The Worker has three bounded lanes (`runtime::lane_of`, no wildcard): Linear
surveys run independently so a hung Linear call never holds back GitHub's answer; a store lane reads and
writes den's own state files (cache, Upstream choices), so a write never waits behind either survey; and
a remote lane runs `gh`, git and kitty. An Effect a full lane refuses goes back to the App as
`Event::EffectRejected` before the next Event. On quit or a signal, `Worker::finish` waits at most
`FINISH_WITHIN_SECS` for queued store writes; remote and Linear work still running is abandoned.
`den --dump COLSxROWS` and the tests use
`runtime::settle`, which performs Effects synchronously through the same
`ports::perform`.

## Rules of the road

- Coverage is honest: a source not read is `NotYetFetched`, never "empty".
  GraphQL errors next to data are `Partial`, never success. No invented counts.
  `Coverage::record` keeps one cross-kind rule: an Owner's Work Item kinds
  (PRs, Issues, Branches, Runs) are never more complete than its Repo list
  (`Incompleteness::RepoListIncomplete`; partial even when the list failed,
  since an Owner's PR query does not depend on it). It is the only place the
  rule lives: fetchers record only what they read and never take the Repos
  state. A kind's own partial reason replaces the derived one; two reasons for
  one source combine by `Incompleteness::rank` (rate limit › whole items missing
  › facts missing from items den has). Sidebar markers and narrowed
  empty states use `app/view/coverage::scope_complete`; All Owners is
  `cache::survey_complete`, the only gate for "Nothing needs you".
- Facts are what GitHub said; Decisions are what den concluded. Don't put rules
  in fetchers or facts in the ViewModel builders.
- Tests go through the two seams (plus thin adapter checks in
  `tests/github_source.rs`). Test helpers: `tests/support/build/` (Observation
  and per-kind builders), `fakes.rs` (fake ports, scripted GraphQL), `harness.rs`
  (drive the App with fake ports).

Detail text is paged after wrapping, in both the pane and the narrow-screen
sheet. `Page Up` / `Page Down` cycle through all pages without changing the
selected Work Item; the detail label shows the page count and keys. Changing
the selection or resizing starts at page one. Launch-sheet editing keeps its
own keys.

PR list coverage (`PullRequests`) and follow-up coverage (`PullRequestDetails`)
are separate. Missing checks or reviews still mark the item incomplete, but a
fully read open-PR list can remove closed PRs from the cache. Successful Branch
and Run reads record complete per-Repo entries even when the Owner list is
partial. Cache format 12 (milestone 2's merged shape: the Linear part with
Linear viewers, Linear Issues with their listing source and attachments, team
states and its own survey time; reviews with their commit and author kind, PR
details with the head they were read at; Linear errors alongside data with a
count of those not kept; #37's Landing Group member states and unanswered-read attempts) rejects older
snapshots, milestone 1's format 4, the per-ticket format 7s, the merged 8,
feat/37's 9 and integrate/m2-wave3's 10 and format 11 included, and rebuilds them with a
fresh survey. Job records are format 4 (a `JobSubject`, stored under a pinned name:
`"github"`, or #40's `"landing_group"`; and #39's optional `permission_mode`) and
still read format 3 (no Landing Group subject), format 2
(format-2 files from before the pin, which stored `"GitHub"`, included) and
milestone 1's format 1, indented while the file fits its bound and compact
when only that fits (milestone 1's indented records grow when converted). A
file of a newer format is refused as a newer den's, never overwritten, so
every new `JobSubject` variant (and any new record field an older den must
not drop on its next append) bumps `JOBS_FORMAT`. The Upstream state format
is unchanged. Files
milestone 1 wrote are kept as fixtures in `tests/fixtures/milestone-1/`.

Linear sources are recorded as `Source::Owner { owner, kind:
SourceKind::Linear(..) }`, keyed by the Owner whose Linear Workflow reads them,
so the per-Owner rules (dropping unwatched Owners from the cache, Owner Scope
coverage, `survey_complete`) apply to them unchanged. They are not in
`SourceKind::WORK_ITEMS` (an incomplete Repo list never marks them partial)
and `Coverage::applicable_to` never gives them to a GitHub Work Item (the PR
rules add an Owner's incomplete Linear Issue lists to a Merge PR's own
coverage, #37). An Owner
without a Linear Workflow records none, so it can't make "Nothing needs you"
false; a recorded one that isn't complete does. An Owner with one always has
every Linear source its workflow reads recorded (`LinearWorkflow::linear_sources`:
the viewer and assigned issues, plus team states and start-team issues when
it names start teams or states); `App::record_unanswered_linear` records not
yet fetched for any the Linear source said nothing about, after every merge
and at cache load. A GitHub answer's own Linear coverage, if any, is ignored.
A Linear Issue's applicable coverage is its Owner's Linear sources and its
Owner's `MemberStates` (#37), without the GitHub viewer; the Linear Issue
rules keep `MemberStates` only on an issue with a member not open and not read
merged. `SourceKind::MemberStates`
is recorded per Owner by the member-state read only; it is neither a Work Item
list nor a Linear source. Linear facts are kept across surveys like GitHub's (#34): a
Linear source read completely replaces its facts, any other keeps the earlier
ones with the age of the Linear survey that read them, and a changed Linear
viewer drops them.

### Land confirmation freshness (issue #30, story 74)

Enter on a ready Land sheet starts a fresh survey round through the existing
GitHub and Linear read ports. It waits for both sources and any follow-up member
state reads before replanning; earlier in-flight surveys cannot authorize the
launch. Failed or incomplete relevant reads leave the sheet retryable. Changes
to landed members, their heads, held members or the first target require renewed
confirmation. Escape cancels the pending launch even when reads finish later.
The executor still checks heads immediately before workspace effects. These
reads are not an atomic service transaction: later changes can still race them.
Regression coverage lives in `tests/app_land_job.rs`.
